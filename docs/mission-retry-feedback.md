# 미션 재시도 실패 사유 전달 — 2단계 첫 비교

기존 미션 생성은 검증에 실패해도 동일한 요청으로 전체 15개를 다시 생성한다.
이번 변경은 다음 시도에 직전 실패 사유를 전달해 같은 오류의 반복을 줄이는 실험이다.

- 최초 요청, 모델, 시스템 프롬프트, 출력 상한 4096, 최대 3회 시도, 서버 검증기와 fallback 선택을 유지한다.
- 길이 오류에는 실제 글자수와 허용 범위, 문법 오류에는 검사 사유, 중복에는 과거 후보 예시를 전달한다.
- 난이도 분포 오류에는 실제 개수와 난이도별 5개 기준을 전달한다.
- JSON 파싱 오류에는 고정 형식 안내만 전달한다. HTTP/API 오류 본문은 전달하지 않는다.
- 유형별 예시는 최대 2개, 생성 필드 예시는 40자까지 전달한다. 전체 응답을 다시 입력하지 않고 이전 실패 안내를 누적하지 않는다.
- 부분 후보 수정은 이번 변경에 포함하지 않는다. 전체 15개 재생성에서 실패 사유 전달만 먼저 비교한다.

## 활성화와 되돌림

`openai.mission.retry-feedback-enabled`의 기본값은 `false`다. 기존 서버 설정에서는
동작과 `baseline-v1` 기록을 유지한다. `true`일 때 작업 버전은 `mission-retry-feedback-v1`이다.
실제 비용·품질 평가 후 활성화 여부를 판단하며, 키 변경은 필요하지 않다.
Spring 환경변수는 `OPENAI_MISSION_RETRY_FEEDBACK_ENABLED=true`다. 다시 `false`로 설정하면
기존 재시도 요청으로 돌아간다.

## 검증

모의 API 테스트는 실패 유형별 안내, 첫 요청 유지, 실패 안내 교체, HTTP 오류 본문 제외,
최대 시도 후 실패·fallback, 비활성 상태의 동일 요청을 확인한다.
전체 단위 테스트 136개가 통과했다.

실제 API 비교는 별도 태스크이며 일반 테스트와 CI에서 실행하지 않는다.
기존 환경변수 또는 기존 `env.properties`의 키를 읽고 키를 새로 만들거나 변경하지 않는다.

```bash
JAVA_HOME=/opt/homebrew/opt/openjdk@21/libexec/openjdk.jdk/Contents/Home ./gradlew missionRetryEval --offline
```

가상 목표 3개 × 기존/변경 각 1회, 최대 18회 호출이다. 운영 DB는 사용하지 않는다.
각 목표의 조건과 과거 미션 목록(빈 목록), 모델과 검증 규칙을 동일하게 맞춘다.
실행 순서는 목표별로 번갈아 설정하지만 작은 표본과 캐시 차이에 따른 편향을 제거하지는 못한다.
리포트는 `build/mission-retry-eval/<timestamp>/results.json`과 `telemetry.log`에 저장한다.

동일 실패 조건의 단일 재시도 비교는 기존 자연 생성 보고서의 후보에 설명 길이 오류를
주입하고, 양쪽에 동일한 목표·상황을 주어 각각 한 번만 요청한다(총 6회). 실행:

```bash
JAVA_HOME=/opt/homebrew/opt/openjdk@21/libexec/openjdk.jdk/Contents/Home ./gradlew missionRetryEval -PretryEvalMode=controlled --offline
```

실패 사유 전달을 실제로 사용하지만 인위적인 오류이며, 최초 생성 비용이나 전체 재시도 비용은
포함하지 않는다. 기본 natural 모드와 별도로 실행한다. 결과는 `controlled-<timestamp>`에 저장한다.

비교 기준은 첫 시도 통과, 모든 시도의 합산 비용, 자동 재시도, 최종 검증 통과와 fallback이다.
출력 토큰만 비교하지 않으며, 비용 미확인 호출이 있으면 전체 비용은 미확인으로 둔다.
통계적 절감률, 장기 사용자·같은 날 재추천의 중복률, 목표 적합성 전체 평가를 대체하지 않는다.

## 다음 판단

운영 활성화 전 기존/변경의 생성 결과를 검토하고, 재시도 실패 사례와 과거 미션이 있는
재추천 사례의 표본을 추가한다. 통과 여부와 전체 원가가 악화되거나 불확실하면 비활성 상태를 유지한다.
정상 후보를 보존하는 부분 수정 방식은 이 비교 이후 별도로 평가한다.

## 부분 수정 비용 비교 (평가용 프로토타입)

운영 서비스와 분리된 `PartialMissionRepairCostEvaluationTest`에서 전체 재생성과 부분 수정을 비교한다.
운영 프롬프트·키·설정·DB는 바꾸지 않는다. 실행:

```bash
JAVA_HOME=/opt/homebrew/opt/openjdk@21/libexec/openjdk.jdk/Contents/Home ./gradlew missionRetryEval -PretryEvalMode=partial --offline
```

영어·운동·투자 고정 목표 × 설명 길이 실패 1/3/5개 × 2회 반복 × 두 방식이다.
각 방식에서 최대 2회 재시도하므로 실제 API 호출은 최대 72회다. 측정 추정 비용이 USD 0.50 이상이면
다음 호출을 중단한다. 고정 가상 시드는 `src/test/resources/evaluation/mission-partial-repair-seeds.json`에
포함되어 있다. 이전 평가에서 최초 호출에 검증을 통과한 결과에 설명 길이 오류를 주입한다.

전체 재생성은 운영 baseline과 같이 기존 목표 요청을 그대로 보내 15개를 다시 출력한다.
부분 수정은 동일 설계 기준과 목표 요청에 수정 대상 전체 필드·오류 및 정상 후보 제목·난이도를
추가 입력하고, 수정 대상의 id/content/description/difficulty만 출력하도록 출력 형식을 바꾼다.
출력 상한은 양쪽 4096으로 동일하다. 정상 후보는 서버에 보존하며 대상 누락·중복·추가 id·난이도
변경은 원자적으로 거부한다. 합친 15개에 기존 난이도 분포·길이·문법 검증을 재실행한다.
첫 수정 후에도 실패한 후보는 남은 재시도에서 다시 수정한다. 미통과 결과를 성공으로 집계하지 않는다.
모의 병합 테스트는 정상 후보 유지, 전체 재검증, 잘못된 대상·난이도 거부를 확인한다.

평가 순서는 매 쌍마다 번갈아 배치한다. 모든 호출의 일반/캐시 입력과 출력 비용을 포함하며
실패·재시도 비용도 제외하지 않는다. 재시도 비용은 이번 실제 호출로 측정하고, 환산 총원가는
같은 최초 생성 비용(이전 단일 호출의 실측)을 양쪽에 더한다. 시드를 반복 재사용하므로 환산 총원가는
이번에 최초 생성부터 독립 실행한 원가가 아니다. 월 운영 절감률로 환산하지 않는다.
캐시·실행 순서의 영향을 살피기 위해 캐시 할인을 제거한 환산 비용도 별도로 계산한다.
이는 모든 입력 토큰을 일반 입력 단가로 재계산한 민감도 비교이며 실제 측정·청구 비용이 아니다.

결과는 `build/mission-retry-eval/partial-<timestamp>/`의 `conditions.json`, `results.json`,
`telemetry.log`에 저장한다. 소규모·인위적인 설명 오류·빈 과거 목록 조건이며 목표 적합성,
후보 간 의미 중복, 난이도 분포/JSON 오류, 장기 재추천 및 실제 운영 실패 비중은 별도로 검증한다.
부분 수정은 아직 평가용 코드이고 운영 적용 판단과 구현은 후속 작업이다.
